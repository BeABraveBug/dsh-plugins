# 版本与发布

本文是 DSH 插件集合的版本与发布约定，适用于 plugins/ 下的插件及其发布依赖。具体构建命令、包名、兼容范围与安装方式由各插件的 package.json、README.md 和构建配置提供；本文不假设尚未建立的发布脚本或自动化已经存在。

## 源码同步、版本升级与发布

| 操作 | 含义 | 是否要求其他插件更新 |
| --- | --- | --- |
| 源码提交与推送 | 将选定修改记录为 Git 提交，并将分支上的提交同步到 GitHub | 不要求修改其他插件或升级其版本 |
| 版本升级 | 修改目标插件的版本与更新记录 | 只处理需要更新的插件及必要依赖 |
| 发布 | 为某个版本提供可安装的产物及发布说明 | 不要求重新发布未受影响的插件 |

Git 推送以仓库分支为单位，不是按插件目录推送。分支上其他尚未推送的提交也会随之推送；发布前检查待推送提交，避免把源码同步误解为只上传某个文件夹。

日常开发可以多次提交和同步代码，准备提供新安装版本时再升级版本。仓库根 package.json 设为 private，不作为插件发布，也不要求设置一个驱动所有插件同步升级的总版本。

## 独立版本

每个插件使用唯一包名，以自身 package.json 的 version 为版本来源。发布说明、标签与安装包中的版本保持一致；各插件分别维护 CHANGELOG.md。

版本采用主版本.次版本.修订版本。稳定版阶段，兼容的问题修复递增修订版本，兼容的功能增加递增次版本，不兼容的变更递增主版本。

本仓库对开发期的 0.x 版本约定：修复递增修订版本，新增功能或不兼容变更递增次版本；发生不兼容变更时在更新记录中明确说明，不把 0.x 版本视为稳定兼容承诺。预发布可使用 0.2.0-beta.1 等形式，并标明验证范围。

每次发布记录以下内容：用户可感知的变化、修复、不兼容事项、数据迁移要求，以及受影响的 DSH 兼容范围。未改动的插件无需改写版本或更新记录。

## 标签与 GitHub Release

标签采用 <插件目录名>-v<版本>，例如：

```text
bookshelf-v0.1.0
bookshelf-v0.2.0
another-plugin-v0.1.0
```

插件目录名应在仓库内唯一。标签指向已经验证的源码提交，记录的是整个仓库快照，不是某个目录的独立历史。多个插件可以在同一提交上创建各自的发布标签。

GitHub Release 按插件和版本分别建立，标题清楚标识插件。为 Release 上传对应插件的可安装包及校验摘要；GitHub 自动提供的仓库源码压缩包不等于可安装的插件包。

已经发布的版本和标签不覆盖、不移动。修复发布问题时使用新版本；有问题的版本在发布说明中标明问题与替代版本。

## 安装包与发布渠道

构建目标插件，打包时包含其运行所需的入口、插件清单、静态资源和依赖。PDF worker、字体或阅读组件资源等文件是否齐全，应以实际插件需要为准。

安装包不包含个人书库、阅读进度、凭据、绝对本机路径或开发缓存。检查最终包内容，不能只验证源码目录可运行。

可使用 GitHub Release 托管预构建安装包；需要包管理器安装时，再为插件分别发布 npm 包。每个插件在 README.md 中明确实际采用的渠道和安装方法，不把推送 GitHub 代码视为完成 npm 发布。

插件依赖工作区公共包时，安装包不能依赖开发机的软链接或源码相对路径。公共代码需被正确打包，或作为可获取的版本依赖发布；发布后在仓库外验证安装。

若插件进入市场索引，安装包或对应源码来源可获取后再更新该插件的索引版本。其他插件的索引版本保持不变；索引生成方式另由实际工具配置定义。

## 公共改动的影响

修改公共包、根配置、构建脚本或共享锁文件时，按实际依赖关系确定影响范围。

- 公共代码被打入插件时，使用该变化的插件需要重新构建并发布新版本，才能把变化交付给使用者。
- 公共包独立发布时，先提供可获取的公共包版本，再更新需要使用它的插件依赖并验证。
- 开发工具或锁文件变化不自动要求所有插件升级；检查其是否改变安装依赖、运行行为或最终产物。

只有需要交付变化的插件升级版本。发布独立不代表验证可以忽略公共改动的影响。

## 发布流程

1. 确定本次发布的插件与变更范围，读取各插件的开发说明，确认当前源码和已有修改。
2. 确认目标 DSH 与运行环境，执行适用的类型检查、测试和构建；修复阻断发布的问题，记录未验证范围。
3. 更新版本、更新记录、安装说明和兼容范围；使用仓库实际包管理流程同步必要的锁文件变化。
4. 从待发布内容生成安装包，检查包内文件，在隔离 DSH 配置中验证安装、加载和关键使用流程。涉及状态格式变化时验证已有数据的升级行为。
5. 将发布内容提交，确认版本、源码提交与验证产物对应。按用户授权执行分支推送、标签推送、GitHub Release 或 npm 发布，避免因完成代码开发而自行扩大到远程发布。
6. 从实际发布渠道获取产物，核对摘要与安装方式；如有市场索引，随后更新索引并验证来源可访问。
7. 报告已发布插件、版本、渠道、验证结果与必要升级说明。若仅完成本地准备，明确标为“待发布”。

同一插件的相同版本不并行发布。部分步骤成功后发生失败，先核对远程现状，只补做未完成步骤；不要重复上传不同内容到同一版本。

## 回退与阅读数据

回退单个插件优先安装其已发布的旧安装包，不把整个开发仓库切换到旧标签。旧标签可用于独立检出和排查，但会同时改变该检出中的所有插件文件。

插件版本与持久化数据格式版本分别管理。改变书库、进度或配置格式时，明确迁移规则、备份方式与旧版兼容性。旧版无法读取新数据时，不承诺仅安装旧包即可恢复；先备份并遵循该插件的迁移说明。

升级、卸载或回退插件不应隐式删除个人书库。需要删除用户数据的操作必须与插件安装操作分开，并明确其后果。
