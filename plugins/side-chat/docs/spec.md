# Side Chat 插件产品规格（SPEC）

- **版本**：V1.2（产品要求；不是已实现版本）
- **状态**：已确认的目标行为，独立会话尚待实现
- **目标平台**：DSH 插件环境
- **实现偏好**：TypeScript / React；复用宿主原生右侧栏和模型服务
- **范围**：描述产品行为、交互规范和验收条件；不规定未经验证的具体 API 名称

## 1. 背景与目标

Side Chat 为 DSH 主会话提供右侧的独立 AI 讨论工作区。用户可以围绕主会话的具体问题发起多个独立侧聊，连续追问、引用主会话文字，并按引用情况使用主会话背景作为 reference，而不干扰主会话消息历史。

### 1.1 已确认的产品原则

1. **一对多**：每个主会话（Parent Session）可以关联多个侧聊（Side Chat）。
2. **独立**：每个侧聊独立保有对话历史、输入草稿、待发送引用及上下文设置。
3. **单面板**：在 DSH 原生右侧栏提供一个插件入口；插件内部使用**顶部下拉选择器**切换侧聊，同时只显示一个侧聊。
4. **独立存储**：点击“新建”即创建插件草稿，首次发送后在同一侧聊保留历史。侧聊只出现在插件内。
5. **可恢复**：收起面板不等于关闭侧聊；“关闭并保留”之后可以恢复。
6. **显式引用**：选中文字后显示浮动按钮；只有点击“侧聊提问”才添加引用；默认投递给当前激活侧聊，绝不自动发送。
7. **上下文可控**：首轮有主动引用时围绕引用讨论；首轮没有主动引用时默认使用当前主会话背景快照作为 reference，正文不在侧聊消息区重复展示。背景仅首轮附加，不自动更新；背景预算为8000字符，不等于继承完整模型上下文。
8. **可并行**：多个侧聊可同时运行；切换显示不应中断其他侧聊的任务。

## 2. 术语

| 术语 | 定义 |
| --- | --- |
| Parent Session | DSH 中当前主会话。 |
| Side Chat | 插件管理的一个独立侧聊，拥有自己的草稿、消息历史和管理状态。 |
| Draft Chat | 尚未提交首条消息的侧聊。 |
| Active Side Chat | 某个 Parent Session 当前在右侧面板显示的侧聊；只是选中指针，不是会话运行状态。 |
| Pending Quote | 用户点击浮动按钮确认后、尚未发送的引用。 |
| Sent Quote | 发送成功并作为历史信息保留的引用快照与来源元信息。 |
| Context Snapshot | 某次获取的主会话正文摘录及其来源范围、生成时间等信息；不表示模型提炼的摘要。 |

## 3. V1 功能范围

### 3.1 面板与导航

- DSH 原生右侧栏中仅注册一个 Side Chat 插件入口。
- 顶部包含：当前侧聊标题／下拉选择器、`+` 新建按钮、`···` 侧聊操作菜单。
- 下拉列表分区显示当前 Parent 的 **打开的侧聊** 与 **已关闭并保留的侧聊**。
- 同一插件面板提供统一的只读归档入口，不依赖当前 Parent 存在；能够查阅各 Parent 的归档侧聊，并辨认其原主会话归属。归档仍显示原主会话归属。
- 默认只展示一个激活侧聊；用户可以收起或展开整个面板。
- 切换 Parent 时切换其对应的侧聊集合，并恢复该 Parent 最近激活的侧聊；无侧聊时显示空状态。
- 不在插件内部添加第二层永久侧边导航栏，也不为每个 Side Chat 新建一个宿主级右侧 Tab。

### 3.2 侧聊创建与切换

- 点击 `+` 新建并激活 Draft Chat。
- Draft Chat 可持有草稿、Pending Quotes 和上下文模式。
- 首次发送使用同一侧聊继续对话。新建、发送、恢复和查看历史均不创建 DSH 原生会话。
- 切换侧聊时，不能清空前一个侧聊的草稿、引用或聊天记录。
- 多个侧聊可以同时运行，面板一次只显示一个。

### 3.3 关闭、保留、恢复与删除

- **收起右侧栏**：仅改变面板显示状态；不更改侧聊管理状态、不主动终止运行任务。
- **关闭并保留**：将侧聊从 Open 列表移至 Saved 列表，保留其历史、草稿、引用和来源关系。
- **恢复**：将 Saved 侧聊重新移到 Open 并激活，恢复原有内容。
- **默认归档**：移出日常侧聊列表时保留历史、草稿、引用、背景快照及原主会话归属，移入归档。
- **归档运行中的侧聊**：请求归档后立即禁止新问题、新提交和新任务，但不主动终止归档前插件已接受的当前任务。显示等待当前任务完成的状态，保留其响应与错误，任务终结后完成只读归档；失败或中断也须如实记录。尚在获取背景或尚未被插件接受的发送不得继续提交。
- **归档只读**：归档完成后可查看历史，不允许发送新问题或启动新任务，不按 Saved 侧聊恢复编辑。
- **永久删除**：是独立于归档的操作，必须单独明确确认其数据范围与不可恢复后果；取消不改变数据。删除范围限于该插件侧聊及其数据。失败或结果未知须保留可追踪状态。
- **主会话删除后的处理**：可靠确认主会话已删除后，关联侧聊采用归档保留，按相同规则等待当前任务结束，并可从统一归档入口查看。运行实例 `removed`、列表暂时缺失、加载失败或权限错误均不单独构成删除证明；证据不足时保留原记录并提示待核验，不误归档或删除。

### 3.4 选文与浮动按钮

- V1 捕获范围：**主会话的一条用户消息或 AI 消息内部**的有效文本选择，包含普通正文及代码块。
- V1 暂不支持：跨多条消息选择、主输入框选文、复杂工具输出、侧聊之间相互引用。
- 鼠标选区有效且松开后，在选区附近显示“侧聊提问”浮动按钮。
- 点击浮动按钮：保存引用快照、展开右侧栏、添加到当前 Parent 的当前激活侧聊。
- 如果当前 Parent 没有激活的可编辑侧聊，则自动创建 Draft Chat 并把引用添加进去。
- 不自动发送或切换到其他 Parent。
- 选区改变时更新候选引用；点击空白处取消候选；滚动离开可视区域时隐藏浮层；切换 Parent 时使未确认候选失效。
- 浮层点击前应已保存临时选文快照，以免点击导致 DOM 选区丢失。

### 3.5 引用管理

- 引用在输入框上方以独立卡片呈现，不直接覆盖或改写用户草稿。
- 同一个 Side Chat 的一次发送可包含多条引用；支持查看预览、移除单条引用和清空待发送引用。
- **建议初始软限制**：每轮最多 5 条、每条不超过 8,000 字符；具体阈值可根据性能与实际模型上下文窗口调整。达到限制需明确提示，不静默裁切。
- 每条引用至少保存文本快照、Parent ID、可获得的来源消息 ID；来源失效时仍保留快照。
- 已发送引用作为历史记录的一部分保留，不随着输入区清空而丢失。
- 未确认 Candidate Selection 不得进入发送请求。

### 3.6 上下文管理

- 侧聊首次发送没有主动引用文本时，默认获取当前 Parent 的背景快照作为 reference；首轮有主动引用时使用主动引用，不额外附加主会话背景。
- 自动附加的 reference 正文不在侧聊消息区重复显示；显示与否不改变模型实际收到的内容。
- 背景是有界正文摘录，不得标称为模型已提炼的“摘要”，也不表示继承完整模型上下文；系统／开发者指令、工具授权不因引用背景而继承。
- 快照仅在首次发送时获取并注入，后续追问依赖 侧聊自己的历史，不自动读取或同步 Parent 新消息；首轮只使用主动引用的侧聊也不会在后续无引用时自动补入背景。
- 首次发送需要快照时锁定来源 Parent 及消息截止范围；读取普通用户正文与已完成助手回复，保留角色和时间顺序，排除生成中片段、工具输出及系统／开发者指令。该流程按时间截取，不宣称已按问题相关性筛选。
- 从最近消息向前按长度预算取材，优先保留完整消息，最终按原顺序排列；当前加载窗口不足预算时补读更早历史，直到达到预算或历史读尽，不因页面是否加载过早期消息而任意改变范围。
- 单条消息超过预算而必须截取时，明确标记为节选，不将不完整正文伪装为完整消息。快照保存实际文本、来源、消息范围及获取时间；获取期间新增的消息不改变已锁定的截止范围。
- 获取失败须明确反馈并保留草稿和引用，不将错误当作主会话没有内容或宣称背景完整。发送重试继续使用同一已冻结快照，不静默替换背景。
- 背景正文预算上限为8000字符；预算内包含用于区分用户／助手的角色标签与消息分隔，背景包裹标记与本轮问题不占此预算。
- 侧聊自己的历史继续可用；移除或停止附加背景不抹除此前已进入历史的信息。如需完全隔离，应创建新侧聊。
- 完整上下文 Fork、模型生成摘要不属于 V1。

### 3.7 发送与 AI 执行

- 侧聊使用 DSH 当前配置的默认模型和凭据进行文字问答。模型不可用时提示原因并保留输入。
- 本轮请求逻辑上由 **侧聊历史 + 用户问题 + 主动引用或适用的主会话背景 reference**组成。
- 主动引用及主会话背景 reference 均作为不可信的待分析材料处理，不得被提升为系统指令或工具权限来源。
- 同一侧聊须显示发送状态。超时后先核对原提交状态，避免重复记录或重复调用模型。
- AI 运行中切换侧聊或收起面板不应主动停止后台任务。
- 运行失败或中断时，提示原因并保留已确认保存的消息、引用与背景。用户可在核对原提交状态后重试。
- V1 允许在助手回复完成后一次性显示全文；运行期间仍须展示执行或等待状态。逐字流式显示不作为 V1 验收要求。

## 4. UI 交互规则

| 操作 | 预期反馈 |
| --- | --- |
| 点击顶部标题 | 展开当前 Parent 的侧聊下拉列表。 |
| 点击 `+` | 新建并激活空 Draft Chat。 |
| 选择 Open 侧聊 | 切换当前显示；原侧聊状态不丢失。 |
| 选择 Saved 侧聊 | 恢复为 Open 并激活。 |
| 点击面板收起 | 仅隐藏面板。 |
| 点击关闭并保留 | 移到 Saved；如当前 Side Chat 被关闭，激活其他 Open 或显示空状态。 |
| 默认移出侧聊列表 | 归档并保留数据；有当前任务时先禁止新提交，显示等待任务完成。 |
| 打开统一归档入口 | 只读查看归档侧聊；不要求原主会话存在。 |
| 点击永久删除 | 独立明确确认删除范围，准确反馈底层结果。 |
| 点击选文浮层 | 添加 Pending Quote，展开面板；不发送。 |
| 发送成功 | 已提交的引用进入历史；清除本轮已发送的输入草稿及 Pending Quotes。 |
| 发送未确认 | 不直接清空草稿／引用；先核对服务端是否已接收。 |
| 切换 Parent | 切换侧聊集合；不迁移引用。 |

## 5. 关键验收标准

1. **多会话隔离**：Parent A 的 Side A1、A2 各自保存草稿、引用及历史；来回切换后内容完全对应。
2. **跨 Parent 隔离**：普通侧聊视图切换 Parent 后仅显示其关联侧聊，统一归档入口按原归属展示跨 Parent 的只读记录；A 的未确认选区失效，已确认引用仍留在 A。
3. **独立侧聊**：新建、发送和重载侧聊均不产生 DSH 原生会话。
4. **选文确认**：仅选中文本不创建引用；点击浮层后产生待发送引用，且不会自动发送。
5. **多引用**：能够独立添加／移除引用；发送后可在历史中查到引用快照。
6. **关闭恢复**：Side Chat 从 Open 转到 Saved 再恢复，草稿、引用、历史及配置一致。
7. **并行执行**：Side A 正在生成时切到 B，A 的响应仍正确写回 A；能力受宿主限制时须明确告知。
8. **异步隔离**：A 的背景摘录获取完成时用户已切到 B，不得将 A 的摘录或结果写进 B。
9. **上下文语义**：首轮有主动引用时不叠加背景；首轮没有主动引用时获取 Parent 快照，正文不重复展示。后续追问不自动读取或补入 Parent 背景；当前窗口不足时按预算补读早期历史，按时间取材并优先保留完整消息，超长单条明确标记节选；获取截止范围与冻结文本可核对，获取失败不伪装为空背景。背景正文（含角色标签与消息分隔）不超过8000字符；停止附加不宣称擦除既有记忆。
10. **错误恢复**：首次发送超时或删除失败时不重复提交、不假报成功。
11. **模型与权限隔离**：沿用 DSH 默认模型完成文字问答，无需另填凭据，不修改主会话配置，也不调用工作区工具。
12. **重新加载**：插件重载后可恢复侧聊归属、消息历史、草稿、引用、归档状态和最近激活项。
13. **完整回复显示**：运行或等待状态可辨认，完成后显示助手全文并归属正确侧聊；无需逐字流式显示。
14. **归档只读**：归档侧聊可查看已有历史，但不能发送新问题或发起新任务；不得将其作为普通 Saved 侧聊恢复编辑。默认归档保留记录、历史和原主会话归属。
15. **运行中归档**：请求归档后新提交被拒绝，当前已接受任务继续并正确记录结果；完成、失败或中断后进入只读归档。未接受的异步发送不因等待结束而继续创建或提交。
16. **统一归档查阅**：切换主会话或原主会话删除后仍可进入统一归档视图，找到对应归档侧聊并读取其保存的历史。加载失败与没有归档记录明确区分。
17. **独立删除确认**：归档不触发永久删除；永久删除单独确认，取消无副作用，底层失败或结果未知不假报成功。
18. **旧会话保留**：升级后，原 DSH 侧聊仍可在对应工作区查看和管理。插件不导入或删除这些会话。

## 6. 非目标与待定项

### 6.1 V1 不包含

- 完整主会话 Fork；模型生成摘要；逐字流式显示。
- 点击引用跳回主消息；自动命名；跨侧聊共享上下文。
- 多个侧聊窗口同时可视化、复杂历史树、批量迁移与关联重定向。
- 复杂日志／工具输出、跨消息选区和主输入框引用。
- 文件或截图发送、工作区文件访问、工具执行与审批。后续附件类型取决于模型及接入接口的能力。

### 6.2 旧会话与主会话删除边界

- 由旧版创建的 DSH 侧聊会话及其历史保留在原工作区，由用户在对应工作区管理和删除。插件的统一归档只查阅独立侧聊。
- 主会话自动归档联动需要可验证的删除事实。宿主无法确认时，界面须准确反映这一限制。

## 7. 需求变更原则

本文件为已经审阅通过的 V1 产品基线。若技术验证证明某项能力无法实现，应先记录影响与替代方案，经确认后变更规格；不得将未经验证的宿主 API 假设写成已实现功能。
